## 2. Integration principles and preserved behavior

1. Extend the existing controllers, services, Blade components and design tokens. Keep the current architecture and installed packages. Introduce a small service only for a real shared domain concern.
2. Preserve single-shop checkout, persistent carts, independent Buy Now, variants, product videos/carousels, private messaging, tab-isolated sessions, analytics and existing exports.
3. Preserve official seller/rider profile review by the relevant administrator. A successful submission means a request was saved; it must not silently replace approved information.
4. Preserve product compliance review. Draft, seller availability and administrator compliance are separate concepts. Seller reactivation cannot undo an administrator restriction.
5. Preserve buyer cancellation requests, their existing Ready-for-Pickup cutoff and 24-hour unanswered-request rule. Restore stock/voucher usage only when cancellation is actually approved, exactly once.
6. Preserve QR/manual-code custody, delivery proof/code, hub ownership, dedicated transfer drivers, vehicle verification and weight/capacity checks. A display label or exception request must not imply a physical handover happened.
7. Preserve funded vouchers, commission/order price snapshots, separate COD receipt verification, payout holds, approved settlement rates and refund authorization. Do not change historical balances or adopt workbook example wages as operating rates.
8. Add nullable columns/tables and explicit backfills where needed. Do not reset the database, edit old migrations, delete historical records or silently rewrite duplicate SKUs, old product media or legacy order data.
9. New features must be enforced server-side, including direct POSTs. Maintain role, owner, hub and account-state checks and publish notifications after commit.
10. Some cases will remain **Different by agreed design**, even after a useful integration. Do not promise that all 54 become Aligned by removing the controls above.

These are recommended defaults for review, not applied configuration changes.

Use PSGC hierarchy or the existing manual fallback. | Do not invent house numbers for rural addresses. Incomplete legacy addresses need correction when used/edited; do not invalidate unrelated profile changes. |

Each phase ends with targeted verification, a reviewable diff and an audit update. Later phases must not obscure an incomplete earlier phase.

| Phase | Work package | Existing integration points | Release condition |
| --- | --- | --- | --- |
| P0 | Baseline and migration inventory | Existing audit, routes, models, factories, regression suites | Record current revision/configuration; inventory legacy addresses, duplicate SKUs, historical media and financial recognition. No production record changes. |
| P1 | Account and address validation; buyer-only staged email change | `AccountController`, `ProfileAppearanceController`, `BuyerAddressService`, `StaffProfileService`, existing OTP/auth infrastructure | Consistent validation, password reuse rejection, verified atomic email replacement and preserved profile approvals/tab isolation. Official staff-email changes are outside this phase. |
| P2 | Product lifecycle, historical snapshots, SKU identity and price ranges | `Seller/ProductController`, `Product`, `ProductVariationEditorService`, `ProductMediaService`, `HomeController`, `SearchController`, `PlacePurchaseService` | Draft/private visibility tested across every buyer surface; order history survives retirement/media replacement; concurrent SKU writes protected. |
| P3 | Voucher scheduling, reason messages and cancellation visibility | `Voucher`, seller/admin voucher controllers, `VoucherClaimService`, `VoucherFundingService`, pricing and transition services | Preview/claim/checkout enforce one eligibility decision; reservation, redemption, release and cancellation remain once-only. |
| P4 | Discovery, wishlist, reviews and chat product context | Search, review and direct-message controllers; existing shop/PDP components | No cross-user writes, no unapproved product leaks, historical reviews remain readable and queries remain bounded. |
| P5 | Seller filters and financial report consistency | `SellerOrderController`, `SellerReportController`, `AnalyticsService`, `OrderFinancialService`, withdrawal/payout services | Screen/export recognition reconciles to authoritative transactions; filters/counts share scope; no new credit or payout pathway. |
| P6 | Rider availability, workload, job history and return guidance | Courier/assignment controllers, logistics dispatch, `ParcelLoadService`, `OrderTransitionService`, settlement and exception services | Eligibility checked under locks at offer/accept/dispatch; physical custody and paid/unpaid state remain intact. |
| P7 | Logistics counts/tracking, zone readiness and financial exports | `LogisticsController`, `HubOrderScope`, administrative audits, rate management, remittance services, existing export builders | Counts match linked filters; own-hub scope remains enforced; CSV/XLSX same dataset/totals; zone activation is explicit. |
| P8 | Provider sandbox + durable payment attempts and To Pay | Checkout, order wallet/finance services, buyer tabs, new provider boundary only where needed | Provider decision and sandbox access, defined reservation/refund lifecycle and passing signed-callback/idempotency checks. Independently gated. |
| P9 | Combined regression, browser review and final audit | Existing test suites and new focused integration cases | Updated 54-row evidence matrix, recorded limitations, actual checks/results, migration/rollback record and walkthrough. |

Execution order: **P0 → P1 → P2 → P3 → P5 → P4 → P6 → P7 → P9**. Phase IDs remain stable for case references. P5 runs before P4 because best-selling calculations need an agreed recognition definition. P8 is an independent gated release, followed by its own repeat of relevant P9 checks; P0–P7 can be audited and released without it.

Dependency details: P2 snapshots precede catalog retirement changes and review variant context. P3 eligibility precedes scheduled-voucher UI. P4 seller review management depends on review media/context. P5 recognition precedes best-selling sorting in P4 and financial exports in P7. P6 workload/availability precedes dashboard eligibility badges. P7 approved serviceability precedes a zone becoming purchasable. P8 must reconcile P3 voucher reservations, existing inventory locks and P5 refund/payout recognition before it can be enabled. Pending-seller drafts must also pass their separate applicant-authentication release gate below.

## 6. Schema, compatibility and rollback design

Finalize names only after checking existing migrations and consumers. These are anticipated additive changes, not migrations already written.

| Area | Expected addition | Compatibility / rollback |
| --- | --- | --- |
| Catalog | Separate private draft records with payload/uploads and submission marker; seller availability on submitted products; normalized SKU ownership/uniqueness support. | Implementation refinement: incomplete drafts never enter `products`, so existing catalog queries cannot accidentally expose them. Existing products retain visibility/compliance/archive state. Conflicting SKUs block migration before DDL; retain IDs/data. |
| Order history | Immutable purchased image/variant snapshot and retained media references. | Populate new purchases; backfill only provable existing values with provenance. Existing image paths do not prove what the buyer originally saw. Cleanup must account for snapshots before deleting any files. |
| Vouchers | Nullable `starts_at`, shared eligibility result/reason. | Null start means existing behavior. Keep integer-cent funding, historical claims, usage and budget audit intact. Old application compatibility must be checked before enabling future-dated offers. |
| Reviews | Review media records and revisions; reuse existing order-item variant snapshots and existing unique order/product constraint. | Existing text/star reviews remain.
